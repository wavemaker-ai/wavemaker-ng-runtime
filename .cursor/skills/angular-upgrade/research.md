## Traceability Rule (required)

For every breaking change found in **R1** and **R3**, do one of:
1. Add a row to the **Dual-repo change plan** in `current-state.md`, OR
2. Annotate inline: `[N/A: reason why this doesn't apply to WaveMaker runtime]`

A breaking change acknowledged only with a summary (no plan row, no N/A) fails the Step 2 gate.

### N/A annotation guidance

**Safe to mark N/A** (WaveMaker runtime does not use these):
- SSR / Server-Side Rendering (hydration, `TransferState`, `renderApplication` server path)
- Signal-based APIs (`input()`, `output()`, `model()`, `computed()`, `effect()`) — not used
- Zoneless change detection (`provideExperimentalZonelessChangeDetection`) — always disabled
- New opt-in `@defer` block semantics — not generated by transpiler
- ESBuild-specific builder options (`@angular-devkit/build-angular:application` only) — WaveMaker uses `browser` builder
- New router features that do not remove or change existing APIs (e.g., new `withViewTransitions()` option)

**Do NOT mark N/A without reading the affected code:**
- Lifecycle hook signature changes (`ngOnChanges`, `ngDoCheck`, etc.) — WaveMaker components use all lifecycle hooks
- DI token renames or removals (any `ɵ`-prefixed token) — WaveMaker overrides several Angular internals
- Template compiler internal API changes (`@angular/compiler` `Parser`, `HtmlParser`, `Element`) — §4 and §19
- `RendererFactory2` / `Renderer2` API changes — §13
- `ApplicationRef`, `EnvironmentInjector`, `ViewContainerRef` signature changes — §2, §3
- `RouterOutlet` output or lifecycle changes — §11
- `HttpClient` provider or interceptor API changes — §7
- `NgModule` / `ApplicationConfig` bootstrap changes — §7, §8b, §20
